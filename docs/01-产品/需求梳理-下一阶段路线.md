## 二、逐条解读与现状

### 1）小模型微调 / 蒸馏：文字 → 日程的模型尽量小（0.x B，含参数约 1G）
- **我理解的需求**：现在“截图文字 → 结构化日程”依赖云端大模型（阿里云百炼）。
  希望换成一个 0.5B–1B 级别的小模型，可私有化部署、成本低、可端侧跑；
  “整流”按蒸馏（distillation）理解：用大模型产出训练数据，教小模型学会同样的结构化输出。
- **现状**：端侧 PaddleOCR 已做文字识别；结构化解析在服务端 `AiVisionController`
  → 百炼兼容接口（`CHRONOFLOW_VISION_*`）。没有训练数据沉淀，也没有小模型。
- **差距**：①需要标注/合成数据集（输入文本 → 目标 JSON）；②需要评测集与指标；
  ③需要蒸馏 + 量化 + 约束解码；④端侧推理框架（ONNX Runtime 已集成）。
- **价值**：成本、延迟、隐私三赢；是后续所有 AI 能力的地基。
- **难度**：5（数据、训练、评测、端侧打包，缺一不可）。
- **专利/论文潜力**：**高**。见第四节 P1、W1。

### 2）API 返回速度：5s → 1s
- **我理解的需求**：解析一次要 5 秒，太慢；希望换更小/更快的模型或服务器，
  并用“结构化输出、少输出 token”的方式把延迟压到 1 秒级。
- **现状**：单次调用云端大模型，输出为 JSON；没有缓存、没有流式、没有并发池。
- **可落地的四招**（按性价比）：
  1. **约束解码 / JSON Schema**：只允许输出目标字段，token 数直接砍半；
  2. **提示词瘦身 + 字段可选化**：能不给的字段不给，减少生成量；
  3. **相同输入缓存**（同一段 OCR 文本 24h 内直接命中）；
  4. **小模型替换**（qwen-flash / 7B 级）并做 A/B 评测，保准确率再上线。
- **价值**：5（识别是核心卖点的第一体验）。
- **难度**：3（前 3 招 1–2 天可上线；换模型要评测）。
- **专利/论文潜力**：中。单独“加速”不够新，但“约束解码 + 端云路由 + 缓存”的组合可写。

### 3）弹窗式日程提醒 + 截图分享更详细
- **我理解的需求**：提醒要像 12306 火车票提醒那样“弹出来、信息完整”；
  分享时给一张信息更全的截图/卡片。
- **现状**：已有本地通知（三档声音、渠道、排期），但通知样式是普通通知；
  分享走系统分享（文本为主）。
- **差距**：①Android 大图通知（BigPicture）/展开式通知；②通知内展示时间、地点、参与人；
  ③生成“日程卡片图”用于分享（可复用现有日历渲染）。
- **价值**：4（提醒是日历类 App 的留存关键）。
- **难度**：2（纯客户端，无需新权限）。
- **专利/论文潜力**：低。

### 4）iOS 端
- **我理解的需求**：把 App 做到苹果手机上。
- **现状**：Expo 代码本身跨平台，但仓库只在 Android 上出过包；需要 macOS + Xcode，
  或者用 **EAS Build** 云端构建（不需要 Mac，按次/按月付费）。
- **差距**：①iOS 原生工程生成（`expo prebuild -p ios`）；②推送证书（APNs）与极光 iOS 配置；
  ③隐私清单 Privacy Manifest；④App Store 审核（账号删除、隐私标签）。
- **价值**：4（校园场景 iPhone 占比高）。
- **难度**：3（代码改动小，证书与审核流程重）。
- **专利/论文潜力**：低。

### 5）本地模型 + 实时检测（语音、屏幕信息…提醒）
- **我理解的需求**：模型跑在手机上，授予权限后实时感知（听到的内容、屏幕上的信息），
  主动提醒/生成日程；核心动机是隐私——数据不出设备。
- **现状**：**云端语音输入已上线**（2026-11-01：长按说话 → 百炼转写 → 日程确认页，仅云端、需联网）；**本地实时检测仍未做**。曾试过离线 Whisper，因繁体、准确率与包体问题移除。
- **必须先说清的三个硬约束**：
  1. **Android 限制**：后台持续录音在 Android 14+ 基本不可行；屏幕内容需要 MediaProjection，
     每次投屏都要用户手动确认，无法常驻。
  2. **商店审核**：应用宝对“录音/屏幕读取”属高风险权限，需逐条说明必要性，
     极易被要求整改；这也是上一版把麦克风权限摘掉的原因。
  3. **法律**：在他人不知情时录音可能违法（《个人信息保护法》敏感个人信息 + 单独同意）。
- **建议的合规形态**（先做这个）：
  - 只做**用户主动触发**：点一下“听写/看屏幕”，前台采集 10–30 秒，本地推理，用完即删；
  - 不做后台常驻监听；不录他人对话；屏幕只在用户点“分享/识别”时读取；
  - 端侧小模型（同需求 1）；ASR 当前走云端，若要本地化再评估 sherpa-onnx（离线 Whisper 已因效果移除）。
- **价值**：4（体验上限高，但风险也高）。
- **难度**：5。
- **专利/论文潜力**：**高**（端侧多模态 + 隐私保护架构）。见 P3、W3。

### 6）服务端把截图文字转结构化数据，并保留真实数据做微调
- **我理解的需求**：服务端把 OCR 文字 → 结构化日程；同时把真实样本留存，
  以后用于微调训练。
- **现状**：有解析接口，但没有样本留存、没有脱敏、没有训练用途的授权。
- **关键合规点（不做会出事）**：
  - 训练用途必须在隐私政策里单独说明，并取得**单独同意**（不能混在“提供服务”里）；
  - 原始截图**默认不保留**；只保留脱敏后的文本 + 模型输出；
  - 提供“不参与改进”的开关，且默认关闭训练用途（opt-in）；
  - 留存期限、删除方式写清楚。
- **建议做法**：脱敏（手机号/姓名/地址替换）→ 采样 → 人工抽检 → 训练集版本化。
- **价值**：4（数据是需求 1 的燃料）。
- **难度**：3（工程不难，合规设计难）。
- **专利/论文潜力**：中高（主动学习 / 数据飞轮可写论文）。

### 7）日程指派到人 / 表格导入分配
- **我理解的需求**：老师或班委把任务/日程指定给具体的人（班长、学委、监考人），
  支持表格导入自动分配，老师能看到完成情况。
- **现状**：组织日程可下发给部门/成员（已有），成员导入支持 Excel；
  但“按表格把人 mapping 到具体任务”还没有。
- **差距**：①表格列映射（姓名/学号/任务/时间）；②任务级接收人（现在下发是日程级）；
  ③完成回执与统计视图（老师端）。
- **价值**：5（这是 B 端付费点，校园场景刚需）。
- **难度**：3（复用现有组织与导入能力，主要是产品设计与权限）。
- **专利/论文潜力**：低。

### 8）任务条：按截止日期分级（红橙绿）+ 长度按任务数比例
- **我理解的需求**：任务以“条”的形式显示在屏幕上，颜色表示紧急程度（红/橙/绿），
  长度与任务数量成比例；点开能看到里面的任务。
- **现状**：任务有 `URGENT/HIGH/NORMAL/LOW` 与截止时间，列表有优先级标签；
  没有可视化时间条。
- **建议实现**：以“今天/本周”为时间轴，按截止时间落点画条；
  颜色：≤24h 红、≤72h 橙、其余绿；长度 = 该时间段内任务数占比（最小宽度保证可点）。
  纯前端 + 纯函数计算，容易测试。
- **价值**：4（一眼看懂“这周有多挤”，是差异化体验）。
- **难度**：1。
- **专利/论文潜力**：低。

### 9）日程与待办合一：日程也是待办的一种（2026-10-20 口头补充）
- **我理解的需求**：日程（占一段时间、到点提醒）和待办（要勾掉）本质是**同一件事的两种看法**。
  日历上列出来的议程，也应该能勾“完成”；待办里列的东西，也应该落在日历的时间轴上。
  两个 tab 应该是**同一份数据的两种视图**，而不是两套互相搬家的数据。
- **现状（为什么现在不像“同步”）**：
  - 两张表：`event`（占时间、可重复、可组织下发）与 `task`（有完成状态、优先级、截止时间）；
  - `task.event_id` 只是“挂在某个日程下”，一个日程挂多条待办，不共享状态；
  - 已有的“日程 ↔ 待办互转”（`ConversionService`）是**新建一条 + 把原来那条标 CANCELLED**，
    用户感受是“搬家”，转过去就找不回来了，这正是让人觉得“不同步”的根因；
  - 底部 4 个 tab（日历 / 待办 / 组织 / 我的）里，日历只显示 event，待办只显示 task；
    只有顶部搜索是两个一起搜的。
- **三个层级（按风险从低到高，可以只做前一层）**：

| 层级 | 做什么 | 动到什么 | 人日 | 风险 |
| --- | --- | --- | --- | --- |
| L1 合并视图 | 日历页当天列表里插入“带截止时间的待办”；待办页顶部加一条「今天的安排」 | 纯前端，两次查询在客户端合并 | 3–4 | 低（不动库、不动接口） |
| L2 行为合一 | `event` 增加 `done` / `completed_at`：日程也能勾完成，勾完变灰沉底；待办的 `due_at` 直接画到日历时间轴上；两者新建时共用一套字段（标题/时间/地点/提醒） | 加一列迁移 + 两个接口加字段 + 两个编辑页合并 | 8–12 | 中（提醒的 `target_type` 已支持 EVENT/TASK，不用改） |
| L3 数据合一 | 合成一张 `item` 表，用 `kind` 区分“占时间/要勾掉” | 大迁移：重复日程、例外表、组织下发、回执都要重做 | 25+ | 高，建议 2.0 再评估 |

> 2026-11-01 已落地 L2 的完成状态部分：完成标记落在独立表 `event_completion`（按身份、按重复实例），没有改动 `event` 主表；日历页和待办页的日程都能勾完成。
>
> 同日已落地 L1：日历当天列表合并「日程 + 有截止时间的待办」，按时间排序；没时间的待办仍只在待办页。月历日期点也把待办截止日算进去。

- **建议**：1.2 先做 **L1**，再补 L2 里最小的那一块（**日程可勾完成**）。理由：上架在即，
  L1 零数据库风险，而且它是需求 8（任务条）和需求 7（指派到人）的前置——没有统一时间轴，
  任务条画不出来。
- **做 L2 之前必须先拍板的三件事**：
  1. **重复日程勾一次还是勾全部**：建议默认“只勾这一次”，`event_exception` 已有
     `occurrence_date`，天然能承载；
  2. **组织下发的日程该不该“完成”**：建议用“参加 / 已读”而不是“完成”，那是别人的安排，
     勾掉自己的不等于事情结束；
  3. **要不要保留“占不占我的时间”**（`availability` = BUSY/FREE）：一块时间被占住和被勾掉
     是两件事，建议保留成独立属性，别合进完成状态。
- **合并后的视觉规则（2026-10-20 v2，已按用户手写批注修订）**：
  1. **日历页**只放“今天什么时候有什么事”：日程 + **有截止时间的待办**，按时间排；
     **没时间的待办不进日历页**（用户批注：整块划掉）；
  2. **待办页**：有时间的全在顶部「今天的安排」时间轴上（**不重复列第二遍**，用户批注：圈掉了重复项），
     没时间的在「待安排」，跨天不清空；不再有「待完成」这类多余小标题；
  3. 时间轴上：日程 = 实心圆点/实线卡 + 左侧色条；待办 = 空心圈/虚线卡 + 截止时间；
  4. 勾掉后当天变灰保留、次日不再出现（让用户看得到“今天干了什么”）；
  5. **日历页布局不改**（搜索框 / 整月网格 / 上传入口 / 浮动按钮照旧），只在当天列表里插入待办；
     **不做筛选 chips、不做折叠**（用户明确否掉）。
- **⚠️ 一个必须先定的前提：日程要不要恢复“时长”**。V18 把 `start_at/end_at` 合成了单个 `at`，
  所以现在画不出参考截图里“8:00–9:00”那种时间块。两条路：
  - **加 `duration_minutes`（建议）**：默认空 = 点状事件；填了就画成块，还能做“同一时间撞车”的提示；
  - 保持点状：只显示“8:00 标题”，不做块。
  前者只加一列，迁移风险小，且是“任务条/周视图”的前置。
- **价值**：5（这是“一个 App 管完所有事”的体验地基，也决定后面 AI 解析只输出一种结构）。
- **难度**：L1 = 1，L2 = 3，L3 = 5。
- **专利/论文潜力**：低（属产品模型统一，不构成技术新颖点），但它是需求 8、1、7 的公共前置。

## 五、合规红线（做之前先看）

1. **录音 / 屏幕读取**：不做后台常驻；只做用户主动触发；隐私政策单独列明；应用宝提审前先自查。
2. **训练数据**：默认不保留原始截图；训练用途单独同意、可关闭；脱敏后才入库。
3. **iOS**：需要隐私清单（Privacy Manifest）、账号删除入口、ATT 说明（如涉及追踪）。
4. **AI 相关资质**：若重新上线“AI 对话”，仍需算法备案 + 安全评估；
   但“图片文字 → 结构化日程”属于工具能力，当前版本已按此口径上线，新增能力不要越界成“对话”。
