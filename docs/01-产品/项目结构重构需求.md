# 项目结构重构需求（供评审，先不执行）

> 目标：把一个「所有人都改同一堆文件」的仓库，改成「每人认领一块，互不踩脚」的结构。
> 本文只讲**要拆成什么样、为什么这么拆、怎么验收**，具体搬文件等你点头后再做。

---

## 一、为什么要做

现在的问题，按疼的顺序：

1. **前端是一个大平面**：`app/src/screens` 30 个页面、`app/src/domain` 26 个文件、`notifications` 20 个、
   `vision` 22 个，全部平铺。改「待办」的人和改「登录」的人，改的是同一个目录。
2. **没有边界**：任何页面都能 import 任何 domain 函数，删一个文件不知道会影响谁。
3. **测试混在一起**：41 个测试文件平铺，跑全量才知道谁坏了。
4. **文档混杂**：`docs/` 里同时躺着需求、合规、部署、提审清单、路线图，新人不知道先看哪份。

后端其实已经拆好了（8 个 Maven 模块），问题主要在前端和文档。

---

## 二、现状盘点（实测数字）

| 区域 | 现状 | 问题 |
| --- | --- | --- |
| `app/src/screens` | 30 个文件平铺 | 按功能分不开 |
| `app/src/domain` | 26 个文件平铺 | 纯逻辑与页面没有对应关系 |
| `app/src/notifications` | 20 个文件 | 与提醒、推送、更新混在一起 |
| `app/src/vision` | 22 个文件 | 端侧 OCR 全在这一块，相对独立 |
| `backend-java` | 8 个 Maven 模块（auth/personal/org/admin/support/agent/common/bootstrap） | ✅ 已分好，只需补边界规则 |
| `backend-python` | 60 个 py 文件，与 Java 同语义 | 双实现维护成本高，需决定去留 |
| `web-admin/src` | 50 个文件，pages 平铺 | 与后端模块没有对应 |
| `docs/` | 30+ 份文档混放 | 找东西靠记忆 |

---

## 三、拆分原则（这几条决定成败）

1. **按业务域切，不按技术层切**。不是 `screens/` `services/` `models/`，而是「登录」「日程」「待办」各成一块。
2. **每块自带四件套**：界面 + 逻辑 + 测试 + 说明（README）。领了这一块的人，只看这一个目录就能干活。
3. **只能单向依赖**：模块 → 共享层；模块 ↛ 模块（确需调用时，只能通过对方的 `index.ts` 导出）。
4. **共享层最小化**：只有「两个以上模块真的都要用」的东西才配进共享层；拿不准就先放模块里。
5. **不合并成微服务**：还是一个后端、一个 App，只是目录和依赖关系变清楚——部署方式不变。

## 四、模块划分（8 块 + 共享层）

| 模块 | 负责什么 | 现在散落在哪 |
| --- | --- | --- |
| `identity` 账号身份 | 登录/注册/密码/验证码/换手机号/绑邮箱/实名/注销/资料 | Login、Register、Password、PasswordReset、PhoneChange、EmailBind、RealName、AccountDeletion、ProfileEdit、AvatarCrop + domain 里 loginForm/password/smsCooldown/profile/avatarCrop |
| `calendar` 日程 | 月历、日程编辑、重复规则、地点、提醒设置、分享 | Agenda、EventEditor、EventPicker、RecurrencePicker、ReminderPicker、LocationPicker + MonthCalendar/Wheel* + domain 里 agenda/calendar/eventDraft/recurrence/reminderSchedule/wheelDate/wheelTime/holiday/search |
| `tasks` 待办 | 待办列表、新建编辑、完成勾选、优先级 | Tasks、TaskEditor + domain/taskDraft |
| `org` 组织 | 组织/部门/成员、组织日程下发、回执、组织账号 | OrgTab、OrgEvents、OrgEventEditor、OrgRecipientPicker、OrgAccounts + domain/orgDispatch/orgRecipients |
| `vision` 识别 | 拍照/选图、端侧 OCR、结构化解析、导入确认 | EventImport + vision/* + domain/vision |
| `notifications` 通知 | 本地提醒排期、通知渠道与铃声、极光推送、更新检查 | notifications/* + domain/appUpdate + updater/* |
| `compliance` 合规 | 隐私政策、同意门禁、清单页、法律文本入口 | Legal、PrivacyConsent + domain/legal/consent + docs/legal |
| `ops` 运维运营 | 我的、设置、反馈、关于、版本信息 | Settings、SettingsSection、Feedback + domain/feedback/media/features |

**共享层 `shared/`**：基础 UI（`ui.tsx`/`list.tsx`/`form.tsx`）、主题、API 客户端（`client.ts`/`types.ts`）、
全局 Context、错误映射、测试工具。**共享层不 import 任何模块**。

> 每个模块内部结构统一为：`screens/`、`domain/`、`api.ts`（本模块端点）、`__tests__/`、`README.md`、`index.ts`（唯一出口）。

## 五、目标结构（推荐方案 A：原地模块化）

```
app/src/
├── shared/                  # 跨模块共用，禁止反向依赖
│   ├── ui/                  # ui.tsx list.tsx form.tsx 等基础件
│   ├── api/                 # client.ts types.ts（端点拆到各模块）
│   ├── theme/  context/  types/  testing/
├── modules/
│   ├── identity/{screens,domain,api.ts,__tests__,README.md,index.ts}
│   ├── calendar/{…}
│   ├── tasks/{…}
│   ├── org/{…}
│   ├── vision/{…}
│   ├── notifications/{…}
│   ├── compliance/{…}
│   └── ops/{…}
├── navigation/              # 路由装配（只拼装，不写业务）
└── App.tsx
```

**为什么不选方案 B（彻底 monorepo：`apps/` + `services/` + `packages/`）**：
B 更"教科书"，但要把 `app/`、`web-admin/`、`backend-java/` 全部换路径，
所有脚本（`build_apk.sh`、`deploy_backend.sh`、`publish_apk.sh`）、CI、文档链接全要跟着改，
对**已经上线的版本**风险不划算。A 能达到同样的"互不干扰"效果，改动面小一半。

> 如果你更想要 B，我也可以做，只是工期从 2 天变成 3–4 天，且要重跑一遍全链路验证。

## 六、边界规则（红线，落地时用脚本强制）

| 规则 | 检查方式 |
| --- | --- |
| 模块之间只能 `from '@/modules/calendar'`，不能深路径进别人内部 | `scripts/check_boundaries.py`（自建，跑在测试前） |
| `shared/**` 不得 import `modules/**` | 同上 |
| 每个模块只能有一个 `index.ts` 出口 | 同上 |
| 模块内测试不得依赖别的模块的测试夹具 | 同上 |
| 后端：`admin` 不得直接调 `personal` 的内部 service，只能调 `*Api` 接口 | 新增 ArchUnit 风格单测 |
| Web 管理端页面按后端模块分目录，与服务端模块同名 | 目录约定 + review |

## 七、文件搬运映射（评审重点，按这个搬）

| 现在 | 搬到 |
| --- | --- |
| `screens/*`（30 个） | 按第四节的表分到 8 个 `modules/*/screens/`，无归属的进 `ops` |
| `domain/*`（26 个） | 同上，按功能归位；`errors.ts` 进 `shared/` |
| `notifications/*`（20 个） | `modules/notifications/` |
| `vision/*`（22 个） | `modules/vision/` |
| `components/*`（10 个） | `ui/list/form` → `shared/ui/`；`MonthCalendar`/`Wheel*` → `calendar`；`MapPicker` → `calendar` |
| `api/endpoints.ts` | 按模块拆成 `modules/*/api.ts` |
| `api/client.ts`/`types.ts` | `shared/api/` |
| `context/`、`theme/`、`types/` | `shared/` |
| `App.tsx` 里的路由表 | 抽到 `navigation/`，按模块注册 |

> 搬运一律用 `git mv`（保留历史），**不改任何一行业务代码**；只改 import 路径。

## 九、执行步骤（4 步，每步都能单独跑、单独回滚）

| 步骤 | 内容 | 耗时 | 验收 |
| --- | --- | --- | --- |
| ① 建骨架 | 建 `shared/` 与 8 个模块目录，只放空 `index.ts` + README | 0.5 天 | 能编译 |
| ② 搬文件 | 按第七节 `git mv`，一次性改 import | 1 天 | 280 项测试全绿、typecheck 通过 |
| ③ 加边界 | `check_boundaries.py` + 接进 `npm test` 前置 | 0.5 天 | 违规 0 条 |
| ④ 拆端点/文档 | 拆 `endpoints.ts`、整理 `docs/` | 0.5 天 | 合规检查 20 项绿 |

**全程不动业务逻辑**，出包前后各跑一次冒烟（登录 / 日历 / 待办 / 识别 / 提醒）。

## 十、验收标准（可量化）

- [ ] `npm test -w @chronoflow/app` 仍是 280 项全绿
- [ ] `npm run typecheck -w @chronoflow/app` 通过
- [ ] `python3 scripts/check_compliance.py --strict` 20 项全绿
- [ ] `mvn -o -q compile` 通过
- [ ] `python3 scripts/check_boundaries.py` 违规 0
- [ ] 删掉任意一个模块目录后，其余模块仍能 typecheck（证明真的解耦）
- [ ] 出包 + 装到模拟器，五条主链路冒烟通过

---

## 十一、多人协作约定

1. 每个模块一个负责人，写进 `CODEOWNERS`；改共享层必须拉至少一个人 review。
2. 一个人一次只碰一个模块目录；跨模块的需求先拆成两个 PR。
3. 分支命名 `feat/<模块>-<做什么>`，例如 `feat/tasks-quick-add`。
4. 模块 README 三行：这模块管什么、对外导出什么、依赖谁。

---

## 十二、需要你拍板的 5 个问题

1. 选**方案 A（原地模块化，2 天）**还是**方案 B（monorepo 大搬迁，3–4 天）**？
2. `backend-python`（60 个文件，与 Java 同语义）**继续维护**还是**归档到 archive/**？
3. `chronoflow-agent`（AI 对话，31 个文件）已下线，**归档**还是留着？（推荐归档）
4. 现在 App 已上线，重构放在**独立分支**做完验证再合，还是直接在主分支小步改？
5. 先拆哪一块？建议从 **`vision`（最独立）** 或 **`tasks`（最小）** 开始试水，验证方法论后再批量搬。

> 你确认后我按「先试水一块 → 你看效果 → 再批量」的顺序做，不一次性大改。
